# Graph Service Implementation & Hardening Report

This document provides a comprehensive, production-grade implementation update for the Graph Service repository. It outlines every architectural decision, codebase configuration, custom exception strategy, optimized batch polling, repository query design, validation integration, and testing framework used to compile the final build.

---

## 1. Architectural Blueprint & System Design

Graph Service acts as the topological layer of the Granthan communication framework. It tracks user messages, channels, and lineage relationships to build a navigable conversation tree.

### Graph Topography Representation
- **Nodes**: Represented by the `:Conversation` label containing properties:
  - `conversation_id`: Unique identifier (String UUID).
  - `user_id`: Owner of the conversation context.
  - `title`: Autogenerated or custom-named context descriptor.
  - `status`: Lifecycle states (`ACTIVE`, `DELETED`, `ARCHIVED`).
  - `created_at`: Chronological creation timestamp in ISO-8601 string format.
  - `updated_at`: Last synchronized modification timestamp.
- **Relationships / Edges**:
  - `CREATED_FROM`: Directed edge going from a child conversation node to its direct parent. Used to traverse upwards (e.g., fetching ancestors).
  - `HAS_CHILD`: Directed edge going from a parent node to its immediate child. Used to traverse downwards (e.g., listing children or sub-conversations).

### Global Services Integration Flow
```text
[Kafka Event Broker] 
       │ (conversation.created / updated / deleted)
       ▼
[KafkaConsumerWorker] (Batched getmany() polling loop)
       │ (Normalized payload dictionary)
       ▼
[GraphService] (Validation, Pydantic parsing, lifecycle policy routing)
       │ (Thread-safe execute_write/execute_read routing)
       ▼
[Neo4jGraphRepository] (Cypher execution against driver session)
       │ (Acyclic Graph Storage)
       ▼
[Neo4j Clustered Instance]
```

## 2. Design Patterns & SOLID Compliance

To establish a scalable and robust foundation, the following software design patterns were applied:

### A. Thread-Safe Singleton (Database Connection Manager)
To maximize connection reuse and prevent system resource leaks, the Neo4j driver connection is managed as a Singleton. A double-checked locking mechanism using a mutex (`threading.Lock`) protects it from parallel initialization races:
```python
from threading import Lock
from neo4j import GraphDatabase, Driver

class Neo4jDatabase:
    _instance = None
    _lock = Lock()

    def __new__(cls, *args, **kwargs):
        if not cls._instance:
            with cls._lock:
                if not cls._instance:
                    cls._instance = super(Neo4jDatabase, cls).__new__(cls)
                    cls._instance._initialized = False
        return cls._instance

    def connect(self) -> None:
        if self._initialized:
            return
        with self._lock:
            if not self._initialized:
                self.driver: Driver = GraphDatabase.driver(
                    settings.NEO4J_URI,
                    auth=(settings.NEO4J_USER, settings.NEO4J_PASSWORD)
                )
                self._initialized = True
```

### B. Repository Pattern (Data Storage Abstraction)
A formal repository boundary separates physical database drivers from service business logic. Service modules invoke method interfaces without depending on driver specifics:
```python
from abc import ABC, abstractmethod

class BaseGraphRepository(ABC):
    @abstractmethod
    def create_conversation_node(self, conversation_id: str, **kwargs) -> dict:
        pass

    @abstractmethod
    def create_relationships(self, parent_id: str, child_id: str) -> None:
        pass
```

### C. Factory Method Pattern (Dependency Inversion)
Dependencies are dynamically compiled and injected into FastAPI endpoints using helper methods:
```python
def get_db() -> Neo4jDatabase:
    return Neo4jDatabase()

def get_repository(db: Neo4jDatabase = Depends(get_db)) -> BaseGraphRepository:
    driver = db.get_driver()
    return Neo4jGraphRepository(driver)

def get_graph_service(repo: BaseGraphRepository = Depends(get_repository)) -> GraphService:
    return GraphService(repo)
```

## 3. Database Layer & Cypher Statements

Queries are optimized using parameterized statements to utilize query-plan cache pools in Neo4j.

### Creation Constraint & Indexing Query
```cypher
// Ensure unique conversation lookup paths
CREATE CONSTRAINT conversation_id_unique IF NOT EXISTS
FOR (c:Conversation)
REQUIRE c.conversation_id IS UNIQUE;

// Speed up owner scope searches
CREATE INDEX conversation_user_id_idx IF NOT EXISTS
FOR (c:Conversation)
ON (c.user_id);
```

### Replay-Safe Merge statement
The merge query checks if the incoming event timestamp is newer than the existing node data. This prevents stale events from overwriting fresh node fields:
```cypher
MERGE (c:Conversation {conversation_id: $conversation_id})
ON CREATE SET c.user_id = $user_id,
              c.title = $title,
              c.status = $status,
              c.created_at = $created_at,
              c.updated_at = $updated_at
ON MATCH SET c.title = case when c.updated_at IS NULL OR $updated_at >= c.updated_at then $title else c.title end,
             c.status = case when c.updated_at IS NULL OR $updated_at >= c.updated_at then $status else c.status end,
             c.updated_at = case when c.updated_at IS NULL OR $updated_at >= c.updated_at then $updated_at else c.updated_at end
RETURN c
```

### Traversal Queries (With Stable Pagination)
```cypher
// Get Children
MATCH (c:Conversation {conversation_id: $conversation_id})-[:HAS_CHILD]->(child:Conversation)
RETURN child
ORDER BY child.created_at ASC, child.conversation_id ASC
SKIP $skip LIMIT $limit;

// Get Ancestors
MATCH (c:Conversation {conversation_id: $conversation_id})-[:CREATED_FROM*]->(ancestor:Conversation)
RETURN ancestor
ORDER BY ancestor.created_at ASC, ancestor.conversation_id ASC
SKIP $skip LIMIT $limit;

// Get Descendants
MATCH (c:Conversation {conversation_id: $conversation_id})-[:HAS_CHILD*]->(descendant:Conversation)
RETURN descendant
ORDER BY descendant.created_at ASC, descendant.conversation_id ASC
SKIP $skip LIMIT $limit;
```

## 5. High-Throughput Consumer Worker & Kafka Setup

The `KafkaConsumerWorker` processes events in batches to optimize network utilization. It polls records concurrently and runs database writes inside thread pools to keep the FastAPI event loop responsive.

```python
# app/workers/consumer_worker.py
class KafkaConsumerWorker:
    def __init__(self, graph_service: GraphService) -> None:
        self.graph_service = graph_service
        self.consumer: AIOKafkaConsumer | None = None
        self._running = False
        self._task: asyncio.Task | None = None

    async def start(self) -> None:
        if self._running:
            return
        
        logger.info(f"Starting Kafka consumer worker with group ID: {settings.KAFKA_CONSUMER_GROUP_ID}...")
        self.consumer = AIOKafkaConsumer(
            settings.KAFKA_CONVERSATION_CREATED_TOPIC,
            settings.KAFKA_CONVERSATION_DELETED_TOPIC,
            settings.KAFKA_CONVERSATION_UPDATED_TOPIC,
            bootstrap_servers=settings.KAFKA_BOOTSTRAP_SERVERS,
            group_id=settings.KAFKA_CONSUMER_GROUP_ID,
            auto_offset_reset="earliest",
            enable_auto_commit=False
        )
        await self.consumer.start()
        self._running = True
        self._task = asyncio.create_task(self._consume_loop())

    async def stop(self) -> None:
        if not self._running:
            return
        self._running = False
        if self._task:
            self._task.cancel()
            try:
                await self._task
            except asyncio.CancelledError:
                pass
        if self.consumer:
            await self.consumer.stop()
        logger.info("Kafka consumer worker successfully stopped.")

    async def _consume_loop(self) -> None:
        try:
            while self._running:
                batch = await self.consumer.getmany(
                    timeout_ms=settings.KAFKA_BATCH_TIMEOUT_MS,
                    max_records=settings.KAFKA_BATCH_SIZE
                )
                if not batch:
                    await asyncio.sleep(0.1)
                    continue

                for tp, messages in batch.items():
                    for msg in messages:
                        if not self._running:
                            break
                        try:
                            payload = json.loads(msg.value.decode("utf-8"))
                            if msg.topic == settings.KAFKA_CONVERSATION_CREATED_TOPIC:
                                await self.graph_service.process_conversation_created(payload)
                            elif msg.topic == settings.KAFKA_CONVERSATION_DELETED_TOPIC:
                                await self.graph_service.process_conversation_deleted(payload)
                            elif msg.topic == settings.KAFKA_CONVERSATION_UPDATED_TOPIC:
                                await self.graph_service.process_conversation_updated(payload)
                        except Exception as e:
                            logger.error(f"Error processing message: {e}", exc_info=True)
                await self.consumer.commit()
        except asyncio.CancelledError:
            logger.debug("Consume loop task cancelled.")
        except Exception as e:
            logger.critical(f"Fatal error in consume loop: {e}", exc_info=True)
```

## 6. Critical Business Decisions & Tradeoffs

### A. Soft Deletes vs. Graph Lineage
In hierarchy models, removing an intermediate node orphans child nodes and breaks lineage paths.
- **Tradeoff**: We introduced a soft delete mechanism (`SOFT_DELETE_ENABLED=true`) that flags deleted nodes as `status = "DELETED"`.
- **Outcome**: Lineage traversal runs smoothly across the tree, and the status property tracks deleted context. Physical hard deletes remain available for explicit nodes.

### B. Chronological Event Constraints
With asynchronous processing, update events can occasionally arrive before creation events.
- **Tradeoff**: We set initial parent stubs (nodes created dynamically when a child event references a missing parent ID) to a Unix Epoch timestamp (`1970-01-01T00:00:00Z`).
- **Outcome**: Stubs act as placeholders with older timestamps, which are overwritten when real creation events with newer timestamps arrive.

### C. Manual Commits for At-Least-Once Delivery
Using automatic offset commits in Kafka runs the risk of committing offsets before database transactions finalize, leading to data loss in crash scenarios.
- **Tradeoff**: We enforce manual offset commits after database transaction loops finish.
- **Outcome**: Ensures at-least-once delivery. Duplicate events are safely ignored by database `MERGE` constraints.
